STUDY PURPOSE
The purpose of this study is to demonstrate that MX1 Portable X-ray System’s Software System meets the requirements as stated in MEMO-P01-630 - MX1 Software Requirements Specification as it relates to the following features:
SRS-44.3 - The SS shall utilize Application Programming Interfaces (APIs) that are resistant to web application security threats
OBJECTIVE AND SCOPE
The primary objective of this study is to verify the software system-level requirements set by MedAI for the MX1 Software System and MedAI Device App as documented in MEMO-P01-630 - MX1 Software Requirements Specification as part of the v3.3.0 release.
Scope of this study is limited to the verification of ability of MX1 Software System to handle unexpected or malformed input from 3rd party DICOM software systems and to automatically recover if input data parsing error occurs.
Scope of this study is limited to use cases when MX1 Software System performs DICOM Modality Worklist (MWL) Service Class User (SCU) operations.
REFERENCES
MEMO-P01-630 - MX1 Software Requirements Specification, Rev. G
MATERIALS
MX1 Software System v3.3.0
S10107 DICOM Fuzzer tool v1.0.0
Test Machine (see Test Setup section below for further details)
SAMPLE SIZE
This is a software verification test, and therefore will utilize a sample size of 1.
METHODS
Locations and Personnel Responsibilities
Verification - To be performed at MedAI office building: 100 Main Street Ste 700 Springfield, IL 60001. To be performed by trained MedAI medical engineering staff.
Personnel who verified the outcome/expected result shall enter with the test result their initials and the date the requirement was verified. Screenshot/photo evidence shall be attached when applicable.
Test Setup
Test Machine  - Github Server or Local Runner, or any other machine (virtual or physical) capable of running Docker and Java applications.
Docker Software latest version
Docker is a software platform that allows for the deployment of software applications in standardized OS-virtualized packages called containers. In this protocol, a Docker container will host MX1 software components to allow for running these tests virtually.
JDK with GraalVM and native-image module v 22.1 or 22.2
Software tools used to build and compile Java applications. In this protocol, these tools may be used to build S10107 DICOM Fuzzer Tool prior to running the test.
Git
Source version control tool to allow for cloning S10107 DICOM Fuzzer Tool into the Docker container.
Test plan
Setup and launch S10107 DICOM Fuzzer Tool on test machine using Docker, which will generate a random amount of randomized and malformed MWL records as a response to DICOM C-FIND request.
Setup Capture Presenter component of MX1 Software System with other components mocked.
Launch Capture Presenter component and perform significant amounts (not less than 200) of operations of retrieving MWL record lists targeting DICOM Fuzzer tool.
Collect data.
Review the test execution report summarizing the data.
Investigate and document exceptions (failures or other reported faults) if any.
Test Steps
Checkout mcx-tablet repo using Git
Navigate into capture-presenter-backend module directory
Run command: ./gradlew :test --tests "com.imager.dicom.MwlFuzzTest"
Wait for test execution to complete
Collect test reports from ./build/reports/tests/test/classes/com.imager.dicom.MwlFuzzTest.html
Interpret the results.
Data Analysis
The test report generated shall be reviewed to determine whether Capture Presenter experienced any fault conditions during the course of testing.
If any faults occur, each occurrence shall be assessed to determine and document the root cause.
ACCEPTANCE CRITERIA
The acceptance criteria for passing this verification test shall be as follows:
The DICOM Fuzzer tool test report output indicatest Capture Presenter does not crash due to Modality Worklists (MWL) fuzz testing inputs.
