## Extracted Content
1. PURPOSE
This document provides a detailed overview of the anomalies resulting from MX1 Software System (SS) v3.2.0 testing and identifies the resolution plans.
Each anomaly reference includes the corresponding requirement, verification steps, description of the anomaly, and how the anomaly may be addressed in a future software release, if applicable. Until an anomaly is resolved, user-initiated workarounds or alternative mitigations may be documented if deemed appropriate.
2. SCOPE
This document pertains to the anomalies discovered through MX1 SS v3.2.0 verification activities.

| Related to the following software requirements: SRS-34.2 The SS should update the wireless network connection status in the MedAI Device App every 5 seconds Anomaly Description: Network connection status does not automatically update within 5 seconds. A user-initiated activity (e.g. switching between screens) must occur before network connection status updates. | This anomaly was originally discovered in MX1 SS v3.0.0. A root cause was undetermined as of the v3.0.0 release. As of MX1 SS v3.2.0, the anomaly is still present. The root cause appears to be related to NetworkManager, the Linux program for providing detection and configuration for systems to automatically connect to networks. When the MX1 software services make any request for network status updates to NetworkManager, they do so with the permissions of imager user. When making the request, NetworkManager will return information only about the current or most recent network connection. In scenarios where network information is displayed as expected in ODA, it’s likely that NetworkManager returns the information after running its own independent scan or if commands are made against NetworkManager as root user. A solution for MX1 software services to make requests as root is inadvisable as it requires a complicated and unsecure design. Currently, alternative solutions are unknown. | Display of network is intended to facilitate users in determining their ability to use features requiring a network connection (e.g. send to PACS). The delayed or incorrect status display has no impact on the system’s ability to support those features. This feature has no impact on the primary intended use, safety, or essential performance of the MX1 system. | Workaround - User may close and reopen the MedAI Device App or switch between MedAI Device App screens to trigger the update of the network connection status message. There is no impact to other network connections or communication requirements. Software modification - To be fixed and verified in a MX1 Software System release prior to commercial release of the MX1 System. |
| Related to the following software requirements: SRS-12.26 The SS shall disallow captures when ODA disconnects from CP Anomaly Description: System failed to interlock after tablet was disconnected from cassette AP. | Discovered in MX1 SS v3.2.0, an exact root cause is yet to be determined. It is possible that capture presenter (CP) fails to determine the status of the MedAI Device App (ODA) in the specific scenario when the tablet is disconnected from the cassette AP. If CP is unable to determine the status of ODA, it will be unable to notify cassette orchestrator (CO) over the RTD websocket, leading CO to act as if all interlocks are still met. | This feature is an interlock that is meant to deter x-ray emission without the user having access to certain features designed in accordance with IEC 60601-2-43 (e.g. “Disable X-rays” button).
