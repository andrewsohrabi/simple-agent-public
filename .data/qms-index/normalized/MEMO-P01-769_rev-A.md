## Extracted Content
1. PURPOSE
This document provides a detailed overview of the anomalies resulting from MX1 Software System (SS) v3.2.1 testing and identifies the resolution plans. This document also serves as a record of anomalies present in v4.0.1, as it was released in parallel with v3.2.1. All anomalies that are unresolved on v3.2.1 are unresolved in v4.0.1.
Each anomaly reference includes the corresponding requirement, verification steps, description of the anomaly, and how the anomaly may be addressed in a future software release, if applicable. Until an anomaly is resolved, user-initiated workarounds or alternative mitigations may be documented if deemed appropriate.
2. SCOPE
This document pertains to the anomalies discovered through MX1 SS v3.2.1 verification activities. It also records evidence of anomalies that were found in previous releases but are not yet resolved.

| Related to the following software requirements: SRS-34.2 The SS should update the wireless network connection status in the MedAI Device App every 5 seconds Anomaly Description: Network connection status does not automatically update within 5 seconds. A user-initiated activity (e.g. switching between screens) must occur before network connection status updates. | This anomaly was originally discovered in MX1 SS v3.0.0. A root cause was undetermined as of the v3.0.0 release. As of MX1 SS v3.2.1, the anomaly is still present. The root cause appears to be related to NetworkManager, the Linux program for providing detection and configuration for systems to automatically connect to networks. When the MX1 software services make any request for network status updates to NetworkManager, they do so with the permissions of imager user. When making the request, NetworkManager will return information only about the current or most recent network connection. In scenarios where network information is displayed as expected in ODA, it’s likely that NetworkManager returns the information after running its own independent scan or if commands are made against NetworkManager as root user. A solution for MX1 software services to make requests as root is inadvisable as it requires a complicated and unsecure design. Currently, alternative solutions are unknown. | Display of network is intended to facilitate users in determining their ability to use features requiring a network connection (e.g. send to PACS). The delayed or incorrect status display has no impact on the system’s ability to support those features. This feature has no impact on the primary intended use, safety, or essential performance of the MX1 system. The potential harm that may be caused by this anomaly is operator Inconvenience. | Workaround - User may close and reopen the MedAI Device App or switch between MedAI Device App screens to trigger the update of the network connection status message. There is no impact to other network connections or communication requirements. Software modification - To be fixed and verified in a MX1 Software System release prior to commercial release of the MX1 System. |
| Related to the following software requirements: SRS-12.26 The SS shall disallow captures when ODA disconnects from CP Anomaly Description: System failed to interlock after tablet was disconnected from cassette AP. | Discovered in MX1 SS v3.2.0, an exact root cause is yet to be determined. This anomaly is still present in v3.2.1. It is possible that capture presenter (CP) fails to determine the status of the MedAI Device App (ODA) in the specific scenario when the tablet is disconnected from the cassette AP. If CP is unable to determine the status of ODA, it will be unable to notify cassette orchestrator (CO) over the RTD websocket, leading CO to act as if all interlocks are still met. | This feature is an interlock that is meant to deter x-ray emission without the user having access to certain features designed in accordance with IEC 60601-2-43 (e.g. “Disable X-rays” button). Therefore, this anomaly should be resolved prior to commercial release of the MX1 System. The potential harm that may be caused by this anomaly is non-diagnostic exposure, which results in a negligible tissue reaction radiation harm. | Workaround - There is currently no workaround that may be performed by the user to enforce this interlock. Software modification - To be fixed and verified in a MX1 Software System release prior to commercial release of the MX1 System. |
| Related to the following software requirements: SRS-32.5 ODA shall contain the ability to reset the loading time limit and the set time limit shall persist between resets Anomaly Description: Total exposure time was reset to 0 when reset timer was tapped. | Discovered in MX1 SS v3.2.0, an exact root cause is yet to be determined. This anomaly is still present in v3.2.1. The root cause of the issue is ODA and/or CP are sending requests to the same CO endpoint, which results in clearing both total exposure time and the loading time limit value. Total exposure time should not be cleared when tapping “Reset Timer”. It should only allow for resetting the loading time limit as per SRS-32.5. | This feature is designed in accordance with IEC 60601-2-43. Therefore, this anomaly should be resolved prior to commercial release of the MX1 System. The potential harm that may be caused by this anomaly is operator dissatisfaction. | Workaround - There is currently no workaround that may be performed by the user to avoid clearing both fields. Software modification - To be fixed and verified in a MX1 Software System release prior to commercial release of the MX1 System. |

| Related to the following software requirements: SRS-16.21 The SS shall emit a constant audible warning at 1861 Hz during loading when the maximum air kerma rate at the patient entrance reference point is exceeded Anomaly Description: Device incorrectly reported dose limit exceeded. Maximum dose limit buzzer did not stop as it was supposed to. | This anomaly was originally discovered in MX1 SS v3.2.1. The anomaly may in part be caused by a bug in the firmware. The software on the Jetson is responsible for notifying firmware to enable and disable the dose limit buzzer. In this particular scenario, the emitter was power-cycled while charging. Upon power-cycling, the software on the Jetson reinitializes. The firmware, however, does not, as the emitter PCBA remains powered to support charging functionality. As a result, the firmware does NOT reinitialize, leading to a discrepancy between software and firmware on the emitter and preventing clearing of the dose limit buzzer register. | This feature is designed in accordance with IEC 60601-2-43. Therefore, this anomaly should be resolved prior to commercial release of the MX1 System. The potential harm that may be caused by this anomaly is operator inconvenience. | Workaround - The user may prevent this behavior by disconnecting the emitter from any charger before power-cycling.
